# CloudBees CI: Enabling Configuration as Code (CasC) for a New Customer

Scenario: an existing CloudBees CI installation (operations center + one or more
managed controllers) that was set up and configured manually through the UI,
with **no CasC in place yet**. This runbook covers exporting the existing
configuration into a CasC bundle, sanitizing it for git, enabling CasC on the
operations center (self-config via the **CasC Retriever**), and enabling the
**CasC Controller Bundle Service** so managed controllers can be fed bundles
too.

---

## Prerequisites

- `kubectl` access to the cluster, `helm` with the `cloudbees` repo added
  (`https://charts.cloudbees.com/public/cloudbees`), `git`, `python3`
- A CJOC admin user with an API token
- A git repo to hold the CasC bundle(s) — can be public or private; if
  private, you'll need SSH or username/password credentials for the SCM
  retriever later
- Required plugins (verify, don't assume — check via
  `<cjoc-url>/pluginManager/api/json?depth=1&tree=plugins[shortName,version,enabled]`):
  - `configuration-as-code` (Jenkins core CasC engine)
  - `cloudbees-casc-client` (v1.44+ / CloudBees CI 2.319.1.5+)
  - `cloudbees-casc-shared`, `cloudbees-casc-server`, `cloudbees-casc-items-api`,
    `cloudbees-casc-items-server`
  - These ship bundled with CloudBees CI on modern cloud platforms in
    practice — this check is a formality, not usually a real blocker
- Know your CloudBees license situation: a purchased (non-trial) license's
  cert/key will show up in the export and needs to be handled as a secret
  (see Phase 2)

---

## Phase 1 — Get the existing configuration as a bundle

Two ways to export the *current, live* configuration into CasC bundle files —
use this instead of hand-writing YAML from scratch:

**UI:** Manage Jenkins → **CloudBees Configuration as Code export and update**
→ **Current configuration** → **Download** (zip or individual files)

**API** (scriptable, same result):
```bash
curl -gS -u "<user>:<token>" -o casc-export.txt \
  "https://<cjoc-url>/core-casc-export"
```
Note: the plain endpoint (`/core-casc-export`) returns a redirect — use `-L`
to follow it, or use `/core-casc-export/zipExport` for a zip if your version
supports it (this endpoint's exact availability can vary by version — if it
404s, fall back to the UI download, which always works).

Unzip/split the result — you'll get some subset of:
- `bundle.yaml` (manifest — lists which of the below are included)
- `jenkins.yaml` (the actual JCasC config — security realm, credentials,
  license, system settings, tool installs)
- `plugins.yaml` (plugin list)
- `rbac.yaml` (groups/roles, if using matrix-based RBAC)
- `items.yaml` (jobs/folders — for CJOC, this includes each *managed
  controller's* declarative definition: image, resources, storage class, etc.)

Do the same export for each managed controller you want to bring under CasC,
in addition to the CJOC/operations-center export.

## Phase 2 — Sanitize the bundle before it goes anywhere near git

**Do not commit the raw export.** CloudBees's own docs are explicit that raw
exports "should not be used directly." Concretely:

### 2a. Secrets (hard blockers)
- Any `credentials.system.domainCredentials` entries in `jenkins.yaml` have
  passwords encrypted with **this instance's `master.key`** — not portable,
  and shouldn't be committed even encrypted. Replace with a variable
  placeholder: `password: "${SOME_CREDENTIAL_PASSWORD}"`.
- If this is an **operations center or client controller** bundle (not a plain
  managed controller), the export will include a `license:` block with a full
  **certificate and RSA private key in plaintext**. This is the single most
  sensitive thing in the export. Replace both with placeholders:
  ```yaml
  license:
    certificate: "${CJOC_LICENSE_CERT}"
    key: "${CJOC_LICENSE_KEY}"
  ```
  (For managed-controller-only bundles, CloudBees's guidance is to remove the
  license block entirely rather than substitute it — the controller inherits
  licensing from the operations center.)
- Supplying the real values: create a Kubernetes Secret with these as keys,
  then reference it via `OperationsCenter.ContainerEnvFrom` in Helm (exact
  mechanism in Phase 5) — this injects the Secret's keys as environment
  variables into the CJOC container, which is what resolves `${VAR}`
  placeholders in `jenkins.yaml` at startup. **Never put the real cert/key/
  password values in any file that lands in `pluggable-storage-migration/`,
  the git repo, or anywhere else that could be committed** — write them to a
  location outside any git working directory, delete them once the Secret is
  created.

### 2b. Cosmetic but recommended
- `bundle.yaml`: give it a real `id` and `description` (the export defaults to
  generic placeholders like `"jenkins"` / `"Autogenerated bundle descriptor"`)
- Review `unclassified.location.url` / `adminAddress` and any other embedded
  hostname — for a bundle meant to describe *this specific* instance (not a
  portable template), keeping the real hostname is usually correct and
  necessary; flag it as a conscious decision either way

### 2c. Validation errors you will likely hit — fix these proactively
These aren't hypothetical — they showed up in a real transformation and will
very likely recur for any customer's export:

1. **`rbac.yaml` schema error**: `required property 'groups' not found` /
   `required property 'roles' not found`. The raw export often produces a
   nearly-empty `rbac.yaml` (just `removeStrategy: rbac: SYNC`) that fails
   schema validation. Two paths:
   - If the instance genuinely doesn't use matrix-based RBAC (check
     `jenkins.authorizationStrategy` in `jenkins.yaml` — if it's
     `loggedInUsersCanDoAnything` rather than a matrix strategy), **the
     cleanest fix is to remove the `rbac:` entry from `bundle.yaml` entirely**
     rather than patch `rbac.yaml`'s content. Including *any* `rbac.yaml` in
     the bundle manifest triggers CasC's RBAC configurator, which then
     requires `RoleMatrixAuthorizationStrategy` to be the active strategy —
     if it isn't, you get a second, harder failure:
     `CasCException: RoleMatrixAuthorizationStrategy is not the current
     authorization strategy and it is required.` Adding empty `groups: []`/
     `roles: []` passes the schema check but walks straight into this second
     error — don't go down that path if the instance isn't matrix-RBAC-based.
   - If the instance *does* use matrix RBAC, populate `groups`/`roles` for
     real from what's actually configured.

2. **`advisor` block validation error**: an empty `advisor: {}` (left over
   from the export) fails with `ConfiguratorException: advisor: Invalid
   configuration for CloudBees Jenkins Advisor`. This is CloudBees's opt-in
   health/usage reporting service — a real decision, not just config
   plumbing:
   - **To disable/skip it**: remove the `advisor:` key from `jenkins.yaml`
     entirely.
   - **To enable it**: it requires both `acceptToS: true` and a valid
     `email:` — ask the customer explicitly before setting this, since it's
     opting into sending data to CloudBees:
     ```yaml
     advisor:
       acceptToS: true
       email: "someone@customer.com"
     ```

3. **`workflow-cps is not in the CloudBees Assurance Program (CAP)`** — a
   warning, not a blocker, but worth mentioning to the customer if it shows
   up; it means a plugin in their `plugins.yaml` isn't part of the standard
   supported envelope.

## Phase 2.5 — Managed controller bundles are not the same shape as the OC bundle

Everything above (Phases 1-2) applies per-instance — do the same export +
sanitize pass **separately for each managed controller** you want under CasC,
hitting that controller's own URL (e.g. `https://<controller>/core-casc-export`),
not CJOC's. But a managed controller's bundle differs from the operations
center's in a few concrete ways:

### File list
- `bundle.yaml` and `jenkins.yaml` are required, same as OC.
- `plugins.yaml`, `items.yaml`, `rbac.yaml`, `variables.yaml` are optional,
  same as OC.
- **`plugin-catalog.yaml` is controller-specific** — it doesn't apply to OC
  bundles. Two separate plugin mechanisms:
  - `plugins.yaml` — CloudBees Assurance Program (CAP) plugins, bundled
    directly into the controller image, no internet connectivity needed to
    install.
  - `plugin-catalog.yaml` — plugins **outside** CAP, downloaded from Update
    Centers or a custom URL at controller-provisioning time. **Any plugin
    listed in `plugin-catalog.yaml` (and its dependencies) must *also* be
    listed in `plugins.yaml`** — the catalog says *where to get it from*, not
    *whether to install it*.
  - This directly explains the `workflow-cps is not in the CloudBees
    Assurance Program (CAP)` warning from Phase 2c: if a controller's
    `plugins.yaml` lists a non-CAP plugin like `workflow-cps` with no
    corresponding `plugin-catalog.yaml` entry, expect install problems on
    that controller — add a catalog entry for it.

### `items.yaml` means something different here
- **OC's `items.yaml`** declares *managed controllers themselves* (their
  image, resources, storage class — what we saw in this session's CJOC
  bundle: `kind: managedController` entries for `mc-ebs`, `mc-efs`, etc.).
- **A controller's own `items.yaml`** declares *that controller's actual
  work*: folders, freestyle jobs, pipelines, multibranch pipelines,
  organization folders, template-based jobs. Example shape:
  ```yaml
  removeStrategy:
    items: "none"        # or "remove-all"
    rbac: "sync"
  items:
    - kind: "folder"
      name: "my-folder"
      displayName: "My Project Folder"
    - kind: "pipeline"
      name: "my-pipeline"
      definition:
        cpsScmFlowDefinition:
          scriptPath: "Jenkinsfile"
          scm:
            gitSCM:
              userRemoteConfigs:
                - userRemoteConfig:
                    url: "git@github.com:org/repo.git"
              branches:
                - branchSpec:
                    name: "*/main"
  ```
- Item creation via CasC on a controller needs the
  **`cloudbees-casc-items-controller`** plugin — check it's installed
  alongside the other CasC plugins from the Phase 0 prerequisites check.

### License: remove, don't substitute
Per CloudBees's own transform guidance: **"Remove (managed controllers) or
update (operations center and client controllers) the license information."**
A managed controller inherits its license from the operations center — its
`jenkins.yaml` should have the `license:` block **deleted entirely**, not
replaced with `${VAR}` placeholders like we did for the OC bundle. There's no
per-controller license secret to wire up.

### Bundle naming
Each controller's `bundle.yaml` `id` must be unique across *all* bundles in
the repo (OC's and every controller's) — CloudBees's docs are explicit that
duplicate bundle names silently fail to sync.

## Phase 3 — Commit the sanitized bundle to git

Directory convention: `casc-bundles/oc/` for the operations center bundle,
`casc-bundles/<controller-name>/` for each managed controller bundle — each
needs a **unique** `bundle.yaml` `id`, since CloudBees's docs are explicit
that bundles with duplicate names won't sync.

```bash
git clone <your-repo-url>
mkdir -p casc-bundles/oc
# copy in the sanitized bundle.yaml / jenkins.yaml / plugins.yaml / items.yaml
git add casc-bundles/oc
git commit -m "Add CJOC CasC bundle"
git push
```

## Phase 4 — Create the Kubernetes Secret for externalized values

```bash
kubectl create secret generic cjoc-casc-secrets -n <namespace> \
  --from-literal=CJOC_LICENSE_CERT="$(cat /path/to/license-cert.pem)" \
  --from-literal=CJOC_LICENSE_KEY="$(cat /path/to/license-key.pem)" \
  --from-literal=SOME_CREDENTIAL_PASSWORD='<real value>'
```
Delete the local plaintext files immediately after.

## Phase 5 — Helm values: enable both CasC mechanisms

Two independent features, both needed here:

### 5a. CasC Retriever — CJOC pulls and applies its own bundle from git
```yaml
OperationsCenter:
  CasC:
    Enabled: true
    Retriever:
      Enabled: true
      scmRepo: https://github.com/<org>/<repo>.git
      scmBranch: main
      scmBundlePath: casc-bundles/oc
  ContainerEnvFrom:
    - secretRef:
        name: cjoc-casc-secrets
```
If the repo is **private**, add SCM auth via
`OperationsCenter.CasC.Retriever.secrets` (`scmUsername`/`scmPassword` for
HTTPS+PAT, or `sshConfig` referencing a secret with SSH key + known_hosts).
Public repos need nothing here.

### 5b. CasC Controller Bundle Service — serves bundles to managed controllers
```yaml
CascBundleService:
  enabled: true
  createConfig: true
```
This stands up a new `casc-bundle-service` Deployment (2 replicas), Service,
Ingress/HTTPRoute, RBAC, and CRD — but its config Secret is created **empty**
by default (`createConfig: true` just stubs it). It does **not** wire up any
managed controller automatically. After this Helm change:
1. Update the `casc-bundle-service-config` Secret with real connector info
   (pointing at the same or a different git repo/path for controller
   bundles).
2. In the CJOC UI, for each managed controller you want fed this way: open
   its configuration → **Configuration as Code (CasC)** section → select
   **"CasC Bundles From CasC Bundle Service"** → pick the bundle by its
   `bundle.yaml` `description` from the dropdown → **Save**.

   Equivalent as CasC, in the OC bundle's `items.yaml`, under that
   controller's `properties:`:
   ```yaml
   - configurationAsCode:
       cascBundleServiceBundle: <base64("<connectorId>:<bundleId>")>
   ```
   Compute the value with `printf '<connectorId>:<bundleId>' | base64 | tr -d '=\n'`.
   Do **not** use `configurationAsCode.bundle: <bundle-id>` — that property
   doesn't do anything for the standalone Bundle Service; `cascBundleServiceBundle`
   is the one CJOC's own object model actually uses (confirmed by exporting a
   controller already associated via the UI and reading back its live CasC).

### 5c. Known gap — the Bundle Service never authorizes the controller's ServiceAccount
Doing step 1 and step 2 above (or the CasC equivalent) is **not sufficient**.
Symptom: the controller pod never becomes `Ready` — it crash-loops with
`Exit Code: 5` and a `503` readiness probe, retrying against the Bundle
Service and getting HTTP 500s:
```
kubectl -n <namespace> logs <controller>-0
...
WARNING c.c.j.p.a.r.p.Downloader#registerError: Error response from server:
  url=http://casc-bundle-service.<namespace>.svc.cluster.local/casc-bundle-service/api/v1/bundles/download/zip-bundle
  status=500
```
Confirm the cause on the Bundle Service side:
```bash
kubectl -n <namespace> logs -l app=casc-bundle-service --tail=50 \
  | grep "does not have access to any bundle"
```
`WARNING K8sBundleReferenceManagement: Service account
[system:serviceaccount:<namespace>:<controller>] does not have access to any
bundle` confirms it.

**Root cause:** the Bundle Service authorizes each request by looking up the
caller's Kubernetes ServiceAccount identity in a ConfigMap named
`service-account-casc-bundle` in the OC's namespace. This ConfigMap ships
**empty** on Helm install (there's no chart value that populates it — its
template only does a `lookup`-and-preserve of whatever's already live, it
never generates content), and — as of chart `cloudbees-core-3.36986.0` /
bundle-service image `cloudbees-casc-bundle-service:779.0c64d59bde91` — CJOC
never writes an entry into it after the UI/CasC association above, even
though CJOC's own ServiceAccount has the RBAC (`create`/`get`/`update` on
configmaps) to do so. This holds true whether you use the UI or the
`cascBundleServiceBundle` CasC property — neither path writes this ConfigMap.

**Workaround** (undocumented internal object, not a supported long-term
config path, but it persists across `helm upgrade` thanks to the
lookup-and-preserve template behavior — repeat per controller):
```bash
# 1. ConfigMap key = base64 (no padding) of the controller's SA identity
KEY=$(printf 'system:serviceaccount:<namespace>:<controller>' | base64 | tr -d '=\n')

# 2. bundleRef value = base64 (no padding) of "<connectorId>:<bundleId>"
#    (same value as the cascBundleServiceBundle property above)
REF=$(printf '<connectorId>:<bundleId>' | base64 | tr -d '=\n')

# 3. Patch it in
kubectl -n <namespace> patch configmap service-account-casc-bundle --type merge -p \
  "{\"data\":{\"$KEY\":\"{\\\"bundleRef\\\":\\\"$REF\\\",\\\"url\\\":\\\"\\\"}\"}}"
```
Verify: the controller's next retry (or delete the pod to force one) should
log `Performed the action download with accepted result` instead of
`status=500`, and the pod should reach `1/1 Ready`.

The `{"bundleRef": ..., "url": ...}` shape was reverse-engineered from the
Bundle Service's own stack traces (class
`com.cloudbees.casc.bundle.service.bundles.K8sBundleReferenceManagement$BundleReferenceAndUrl`)
by deliberately feeding it malformed values and reading the resulting
Jackson exceptions — it is not documented publicly. Treat this as a stopgap
and **file a CloudBees support case** citing the exact log line, the chart
and image versions above, and the fact that CJOC's RBAC already permits the
write it never makes.

### Applying
```bash
helm get metadata <release> -n <namespace>   # confirm exact chart version first
helm upgrade <release> cloudbees/cloudbees-core \
  -n <namespace> \
  --version <current-chart-version> \
  --reuse-values \
  -f casc-values.yaml \
  --dry-run   # review the diff before applying for real
```
Then drop `--dry-run` to apply.

**What to expect in the dry-run diff:** a new init container on the CJOC
StatefulSet (`casc-retriever-init-container`) that checks out the bundle
*before* CJOC starts — if this fails, CJOC won't start at all. A new sidecar
(`casc-retriever`) polls for updates afterward (default every 20 min). The
main `jenkins` container gets `-Dcore.casc.config.bundle=...` and
`envFrom: secretRef: cjoc-casc-secrets` added. Plus the whole new
`casc-bundle-service` Deployment/Service/RBAC/CRD set.

**This restarts CJOC.** Have a rollback plan ready:
```bash
helm rollback <release> <last-known-good-revision> -n <namespace>
```

## Phase 6 — Watch it come up, diagnose failures fast

```bash
kubectl get pods -n <namespace> -w
```

If the CJOC pod crash-loops, check the init container first (it runs before
anything else, so it's the most likely failure point), then the main
container:
```bash
kubectl logs cjoc-0 -n <namespace> -c casc-retriever-init-container
kubectl logs cjoc-0 -n <namespace> -c jenkins --tail=1000 --previous > /tmp/crash.log
grep -n "BootFailure\|Failed to initialize Jenkins\|ConfiguratorException\|InvalidBundleException" /tmp/crash.log
```
The real root-cause line is usually `SEVERE hudson.util.BootFailure#publish:
Failed to initialize Jenkins`, immediately followed by the actual exception —
search for that exact phrase rather than trusting a small `--tail` window,
since the meaningful error can be buried under hundreds of unrelated startup
log lines.

**One more side effect to expect:** the first time `items.yaml` gets applied
via CasC for controllers that already exist, CJOC may trigger a **reprovision**
of those controllers (new pods with new pod-hash suffixes appear alongside the
existing running ones) — even if nothing in `items.yaml` actually changed
versus their current live config. This is generally safe (old pods keep
running until new ones are healthy), but can get stuck if the cluster lacks
spare capacity (watch for `FailedScheduling: Insufficient cpu` combined with
the autoscaler being at its max node group size). If capacity is tight,
either free some up, increase the node group's max size, or delete the stuck
`Pending` reprovision pods to cancel the attempt — the original pods are
unaffected either way.

```bash
# confirm CJOC picked up the bundle (both should print the retriever's health/version)
kubectl logs cjoc-0 -n <namespace> -c casc-retriever --tail=50

# confirm the CasC status page in the UI shows the bundle as applied, not "invalid"
```
Visit **Manage Jenkins → CloudBees Configuration as Code export and update**
(or the CasC status page) to confirm the currently-applied bundle version/ID

## Summary of gotchas (repeat offenders across customers)

- Raw exports need sanitizing — license cert/key and credential passwords are
  the two hard blockers, always assume they're present for an OC/client
  controller bundle.
- `rbac.yaml`'s schema wants `groups`/`roles` even when unused — but adding
  them empty triggers a *different*, harder requirement
  (`RoleMatrixAuthorizationStrategy`). If the customer doesn't use matrix
  RBAC, just drop `rbac.yaml` from `bundle.yaml` entirely.
- `advisor: {}` empty blocks fail validation — decide explicitly whether to
  enable (needs `acceptToS` + `email`) or remove it, don't leave it as a
  stub.
- License/credentials get externalized via a Kubernetes Secret +
  `OperationsCenter.ContainerEnvFrom`, resolved through ordinary `${VAR}`
  CasC variable substitution — there's no separate Helm-native "upload your
  license" mechanism beyond the trial/evaluation flow.
- Enabling `CascBundleService` alone doesn't feed any controller a bundle —
  that needs a populated connector config plus a per-controller UI selection
  (or the `configurationAsCode.cascBundleServiceBundle` CasC equivalent — not
  `configurationAsCode.bundle`, which does nothing here).
- **Known gap:** even after the correct UI/CasC association, the Bundle
  Service will 500 forever because CJOC never writes the controller's
  ServiceAccount into the `service-account-casc-bundle` ConfigMap it needs to
  be authorized. See Phase 5c for the confirmed symptom, root cause, and a
  manual `kubectl patch` workaround. File a CloudBees support case — this is
  a product gap, not a config mistake.
- Applying `items.yaml` for the first time can trigger unexpected
  reprovisioning of existing managed controllers — check cluster capacity
  before applying, not after.
- A managed controller's bundle isn't a smaller copy of the OC bundle — its
  `items.yaml` means jobs/folders (not controller definitions), it can have a
  `plugin-catalog.yaml` the OC bundle doesn't use, and its license block
  should be **removed**, not variable-substituted, since it inherits
  licensing from the operations center.

# Part 2 — OC-Hosted Git-Backed CasC Bundles for Managed Controllers

This is a **different mechanism** from Phase 5b/5c above. Phase 5b is the
standalone **CasC Controller Bundle Service** (a separate `casc-bundle-service`
Helm-deployed microservice, associated via `cascBundleServiceBundle`). This
part covers OC's **built-in, embedded** bundle library (`bundleStorageService`
in OC's own `jenkins.yaml`) — no extra Deployment/Service required, just an
OC-side JCasC setting. Both can coexist in the same cluster feeding different
controllers; don't conflate the two properties.

Use this mechanism when OC already has (or you're adding) a
`bundleStorageService` pointed at a git repo, and you want managed controllers
to pull their bundle straight from that repo without standing up the separate
Bundle Service.

## Phase 8 — Confirm the mechanism is enabled and *visible*

OC's own `jenkins.yaml` (its `unclassified` JCasC section) needs both of
these:

```yaml
unclassified:
  bundleStorageService:
    activated: true
    checkOutTimeout: 600
    pollingPeriod: 120
    purgeOnDeactivation: false
    activeBundle:
      name: "<retriever-name>"
      polling: true
      retriever:
        SCM:
          defaultVersion: "main"
          scmSource:
            git:
              id: "<scm-source-id>"
              remote: "https://github.com/<org>/<repo>.git"
              traits:
              - "gitBranchDiscovery"
cloudBeesCasCServer:
  disableRemoteValidation: false
  visibility: true
```

**`cloudBeesCasCServer.visibility` is the load-bearing setting and it is easy
to miss.** If it's `false` (the value it's *shipped* with in at least one
observed environment), everything downstream looks fine and silently doesn't
work:
- The bundle retriever polls successfully, checks out the repo, and the
  bundle validates cleanly (`structural-validations.yaml` shows all-INFO, no
  errors) — nothing here signals a problem.
- The "CasC Bundles From Operations Center" dropdown on a managed
  controller's config page is simply **empty** — no error, no bundles listed.
- A managed controller wired to `configurationAsCode: {bundle: <id>}` (or
  even the older `cascBundleSource: OC_CASC` + `bundle: <id>` form)
  crash-loops on boot with:
  ```
  SEVERE  hudson.util.BootFailure#publish: Failed to initialize Jenkins
  java.io.FileNotFoundException: Bundle file /var/casc-bundle/bundle-link.yaml not found.
  Caused: com.cloudbees.jenkins.cjp.installmanager.casc.InvalidBundleException: Invalid configuration bundle: ...
  ```
There is no error message anywhere pointing at `visibility` — it was found by
inspecting the live object on the OC pod directly:
```bash
kubectl -n <namespace> exec cjoc-0 -c jenkins -- \
  cat /var/jenkins_home/com.cloudbees.opscenter.server.casc.BundleStorageConfiguration.xml
```
If `<visibility>false</visibility>`, set it to `true` via CasC (above) and
restart OC (Phase 11) — don't just flip it by hand in the UI, since that
won't survive the next bundle reload from git.

## Phase 9 — Repo layout: one bundle per folder, folder name = bundle ID

The retriever scans the **entire repo** (not just one configured
subdirectory) for any folder containing a `bundle.yaml`, wherever it's
nested. The folder's own name — not its full path — becomes the bundle ID:

```
cb-gitops/
└── casc-bundles/
    ├── oc/                # OC's own bundle, id: "oc"
    │   ├── bundle.yaml
    │   ├── jenkins.yaml
    │   └── items.yaml
    └── mc/
        ├── mc-ebs/         # bundle id: "mc-ebs"
        ├── mc-fsx-ha/      # bundle id: "mc-fsx-ha"
        └── mc-efs/         # bundle id: "mc-efs"
```

Each managed-controller bundle folder needs the same file set/sanitization
rules as Phase 2/2.5: `bundle.yaml` + `jenkins.yaml` required; `plugins.yaml`,
`plugin-catalog.yaml`, `items.yaml` as needed; **no `rbac.yaml`** if the
instance doesn't use matrix RBAC (drop it from `bundle.yaml`'s manifest, same
as Phase 2c); license block and `unclassified.operationsCenterRootAction`
(a live connection secret, not durable config) **removed entirely** from
`jenkins.yaml`; `advisor` set explicitly (`acceptToS: true` + `email`), never
left as an empty `{}`.

## Phase 10 — Wire a managed controller to its bundle

In the OC bundle's `items.yaml`, under that controller's `properties:`:

```yaml
- kind: managedController
  name: mc-efs
  properties:
  - configurationAsCode:
      bundle: main/mc-efs
```

The value is `<branch>/<bundle-folder-name>` — OC resolves a bare
`bundle: mc-efs` (no branch prefix) to this same qualified form internally
using the retriever's `defaultVersion` as the implicit branch, but writing it
out explicitly keeps git as the literal source of truth for what's live
(confirm what's actually applied by re-checking the item's live config in the
UI/export after it comes up).

Do **not** use `cascBundleSource: OC_CASC` here — with `visibility: true` and
this repo layout, the plain `bundle:` property is sufficient; `OC_CASC`
implies a bundle uploaded directly to OC's own local store (a different,
unused path in this setup) and will crash-loop identically to the
`visibility: false` symptom above.

## Phase 11 — Push through git

Direct pushes to `main` are commonly blocked by repo policy (a
pre-push/CI hook). Use a branch + PR even for a one-line config change:

```bash
git fetch origin main
git checkout main && git pull origin main
git checkout -b fix/<short-description>
# ...edit casc-bundles/... ...
git add <files>
git commit -m "<message>"
git push -u origin fix/<short-description>
# open the PR at the URL git prints, merge via the GitHub UI
```

## Phase 12 — Apply and watch it come up

Merging to `main` alone is **not enough** — OC's own bundle and its managed
controller items only get re-applied on an explicit reload, and
`bundleUpdateTiming.automaticReload`/`automaticRestart` are typically `false`
(check `/var/jenkins_home/bundle-update.properties` on the OC pod to
confirm). The reliable way to force it:

```bash
kubectl -n <namespace> delete pod cjoc-0
# wait for it to report Running with all containers ready:
kubectl -n <namespace> get pod cjoc-0 -w
```

This is disruptive (brief outage for the whole operations center — all
managed controllers lose contact with it, license renewal warnings appear in
their logs) — treat it like the "This restarts CJOC" warning in Phase 5's
Applying section, and expect to do it more than once:

- **A specific controller's item may not reprovision on the first restart.**
  Symptom: its logs show `Add CasC JAVA_OPTS for <name>` but never reach
  `PROVISIONING requested` / `PROVISIONED` / `STARTING` in OC's own logs
  (`kubectl logs cjoc-0 -c jenkins | grep <name>`), and no new
  Deployment/ReplicaSet appears for it. A second `kubectl delete pod cjoc-0`
  has reliably unstuck this.
- **A brand-new controller (never provisioned before) may need an extra
  nudge** beyond restart-triggered reconciliation — if it's still not
  progressing after a restart, try a manual "Provision" action on that
  controller's page in the OC UI.
- **Reprovisioning can leave two ReplicaSets for the same controller** — an
  old (stale, pre-fix) one still holding its pod/CPU allocation, and a new
  one that can't schedule because of it (`FailedScheduling: Insufficient
  cpu`). Confirm the old one predates the fix, then clear it:
  ```bash
  kubectl -n <namespace> get replicaset | grep <controller-name>
  kubectl -n <namespace> delete replicaset <old-stale-replicaset-name>
  ```

**Verify a controller actually loaded its bundle** (don't just trust
`1/1 Running` — check the boot log once, since a controller can be Running
on a stale/no bundle too if you didn't clear an old ReplicaSet):
```bash
kubectl -n <namespace> logs <pod> --tail=300 | \
  grep -n "BootFailure\|FileNotFoundException\|Creating items from CasC bundle items section\|jenkins is fully up"
```
Success looks like `Creating items from CasC bundle items section` +
`Jenkins is fully up and running`, no `BootFailure`. Failure is the
`FileNotFoundException: Bundle file /var/casc-bundle/bundle-link.yaml not
found` signature from Phase 8.

## Phase 13 — Bringing a brand-new controller under CasC (no prior config to sanitize)

If the controller has never been provisioned before, there's no existing
config to export up front. Sequence:
1. Scale it up via `items.yaml` (see Phase 14) with **no**
   `configurationAsCode` property yet — let it come up with whatever
   default/autogenerated config CloudBees CI gives it.
2. Once it's `1/1 Running`, export its live config: **Manage Jenkins →
   CloudBees Configuration as Code export and update → Current configuration
   → Download**, on that controller's own URL (not OC's).
3. Unzip, sanitize per Phase 9's rules (license, `operationsCenterRootAction`,
   `advisor`, drop `rbac.yaml`), fix `bundle.yaml`'s `id`/`description` (the
   raw export's description is just `"Autogenerated bundle descriptor"`).
4. Commit the sanitized files under `casc-bundles/mc/<id>/`, add the
   `configurationAsCode: {bundle: main/<id>}` property (Phase 10), push
   (Phase 11), apply (Phase 12).

## Phase 14 — Scaling a managed controller via CasC

```yaml
configuration:
  kubernetes:
    replication:
      config:
        maxReplicas: 0
        replicas: 0      # 0 = scaled down, 1 = up
        targetCPUUtilizationPercentage: 80
```
A controller with no `replication.config` block at all may simply never get
provisioned — add the block explicitly to bring it up.

## Phase 15 — Cluster capacity is zone-scoped, not just cluster-wide

A controller (or OC itself) whose PV is backed by a single-AZ storage class
(e.g. plain EBS `gp3`) is **hard-pinned to that AZ** and can only ever
schedule on nodes there — check with:
```bash
kubectl get pv <pv-name> -o jsonpath='{.spec.nodeAffinity}'
kubectl get nodes -o custom-columns=NAME:.metadata.name,ZONE:'.metadata.labels.topology\.kubernetes\.io/zone'
```
FSx-OpenZFS- and EFS-backed PVs are typically **not** zone-pinned this way.

If cluster autoscaler can't add capacity (`NotTriggerScaleUp: ... max node
group size reached`) and a zone-pinned pod is stuck `Pending` with
`Insufficient cpu`, **freeing CPU cluster-wide is not sufficient** — it has
to be freed in that specific AZ. Scaling down an unrelated controller in a
*different* AZ won't help, even though the cluster-wide CPU math looks fine.
The fix is to move a *non-zone-pinned* pod off the crowded AZ instead:
```bash
kubectl -n <namespace> delete pod <non-zone-pinned-pod>
# scheduler favors the less-loaded node; confirm it landed in the other zone:
kubectl -n <namespace> get pod <new-pod-name> -o wide
```
then retry/restart whatever was stuck.

## Summary of gotchas (Part 2)

- `cloudBeesCasCServer.visibility: false` silently breaks everything
  downstream — no error anywhere, just an empty bundle dropdown and a
  `bundle-link.yaml not found` crash loop. Check it first if a managed
  controller "isn't picking up its bundle" despite the bundle validating
  fine in the store.
- This mechanism (`bundle: <branch>/<id>`) and the standalone Bundle Service
  (`cascBundleServiceBundle`, Phase 5b) are **not interchangeable** — using
  the wrong property for whichever mechanism is actually configured produces
  the identical crash signature either way.
- Merging to `main` doesn't apply anything by itself — OC needs an explicit
  restart, and even then a given controller's reprovisioning can stall and
  need a second restart, or leave a stale ReplicaSet that must be manually
  cleared before the new one can schedule.
- `1/1 Running` isn't proof a controller loaded the intended bundle — always
  grep its boot log for the bundle-loaded/BootFailure signatures.
- Zone-pinned storage (plain EBS) + a maxed-out node group in that specific
  AZ can starve OC itself, not just managed controllers — and the fix is
  zone-aware capacity management, not just "free some CPU somewhere."
